## Title

**Ledger — a double-entry skeleton you cannot lie to**

## One-line pitch (the elevator)

A double-entry ledger where `Σ postings = 0` is the only law: entries are immutable, corrections
are visible, every balance is a fold, and every claim is a tested property. Two applications
inherit the same 2 100-line core — one hides everything, one publishes everything.

## Description (features and functionality)

Ledger is a **skeleton for keeping a book** — not for exploring a file, not for drawing a chart.
An entry is a packet of postings that must sum to zero; a journal is an append-only, hash-chained
list; a balance is always recomputed from the journal, never stored.

- **Append-only, hash-chained.** No function edits an entry. A correction is a *reversal*: a mirror
  entry linked to the original, so the mistake stays visible and the chain proves nothing was rewritten.
- **Five extension points**, one configuration file per application: `defineChart` (accounts),
  `defineRules` (memo → account), `defineEnvelopes` (budgets and rollover), `defineReports`,
  `definePresentation` (theme and locale).
- **Two applications, opposite trust models, same core.** `apps/envelopes` is a household budget —
  private, nothing leaves the browser, one number answers "can I still spend tomorrow?".
  `apps/mutual-aid` is a solidarity fund — public, plain-language, with a hash chain any donor can
  verify offline from a `{entryId, hash}` receipt.
- **A third application built in 16 min 32 s** by someone who had never seen the repository
  (a time bank with a `hour` unit), without a single line changed under `packages/**`.

## Built with Kiro

The full trace lives in `/.kiro` (tracked; a CI job fails if it is ever ignored): 7 steering
files, 8 specs, 5 hooks, 2 read-only agents, 1 skill, 1 power, `KIRO_JOURNAL.md`.

- **Which Kiro surfaces?** The repository is structured for Kiro's IDE (specs + steering +
  `fileMatch` inclusions) and a headless CLI in CI. This machine had no Kiro session, so the
  hook *commands* ran as plain CI gates, and `KIRO_JOURNAL.md` says exactly which surfaces were
  exercised and which were authored but not run — nothing is claimed that did not happen.
- **Custom agents.** `ledger-reviewer` (read-only, confronts a diff with the EARS requirements and
  the accounting rules) and `property-tester` (writes only `*.test.ts`, reports the seed and the
  smallest counter-example). Their checklists are the ones applied during review.
- **Hooks.** `loc-budget`, `immutable-journal-guard`, `property-guard`, `fixture-privacy-guard`,
  `bundle-budget`. Each is a one-line command, and each is duplicated in CI because a
  file-triggered hook never sees edits made outside the agent.
- **Spec-driven development.** Requirements were written *before* the code, with EARS identifiers
  (`LED-F-01` …) that the tests cite. For the contract and the journal this mattered; for the two
  smallest modules the design came out of the tests instead — recorded, not hidden.
- **Steering.** `accounting.md` (the sign convention, the only law, the hash form) kept five
  modules written in parallel consistent; `lean.md` keeps a reason for every refusal. Those two
  made the biggest difference.
- **Property-based testing.** 15 properties (the cahier's `LED-P-01` … `LED-P-15`), seeded,
  at 10 000 cases in the campaign and a 20-seed sweep, all green. PBT caught one *test-side* bug
  (a generator that produced too few entries); no product counter-example surfaced after the
  invariants were formalized — that too is recorded rather than dressed up.
- **Powers.** `new-ledger-app`, used in the unknown-room test to build the third application.
- **MCP.** Not used — `settings/mcp.json` is deliberately empty rather than declaring a server
  that does not exist.

## The problem this solves, and for whom

A ledger is the canonical notebook that a household, an association and a fund all need, and
nobody is served: the text tools (Beancount, hledger) demand a developer, the apps (Actual,
GnuCash, Firefly III) want accounts and servers. **Sarah**, Thursday 26 November 2026, asks one
question — "can I still spend tomorrow?" — and gets one number, nothing uploaded. **Six volunteers**
running a solidarity fund ask "where did the money go?" — and hand every donor a `{entryId, hash}`
they can verify without any tool.

The honest limit is printed, not hidden: the chain proves *coherence*, not that the entries are
sincere, and it proves nothing about the tail someone else could cut. Those limits are part of
the product (`README.md`, the public page, `KIRO_JOURNAL.md`).
